Why I Ditched Asuswrt-Merlin for a Dumb Switch

I was planning to use Asuswrt-Merlin for VLAN segmentation in my home lab. A quick check of the firmware support status and one CVE later, I scrapped that plan entirely.

The plan

When I was setting up my home lab, I needed a way to segment traffic between my Proxmox host, personal devices, and the rest of the network. My first instinct was to flash Asuswrt-Merlin on my existing ASUS router and use it for VLAN management. Merlin is a well known third-party firmware fork that adds features the stock ASUS firmware doesn't have, and it seemed like the obvious choice for someone wanting more control without buying dedicated hardware.

What I found first

Before touching anything I looked up whether Merlin was still actively maintained for my device. It wasn't. My router model was on the end-of-life list, meaning no further security patches. That alone was a yellow flag, running an unpatched firewall component at the edge of a network you're trying to secure is counterproductive. But I kept digging.

The CVE

Searching for known vulnerabilities in the firmware version I would have been running turned up CVE-2017-12754.

CVE ID
CVE-2017-12754
CVSS Score
8.8 High
Published

Type
Stack Buffer Overflow

The vulnerability is a stack buffer overflow in the httpd daemon in Asuswrt-Merlin firmware 380.67 and earlier. A remote attacker can execute arbitrary code on the router by sending a crafted HTTP GET request with a long delete_offline_client parameter in the URL. No authentication required. Remote code execution on the device sitting between your internal network and the internet.

The affected device list was long: RT-AC5300, RT-AC3200, RT-AC68U, RT-AC88U, RT-AC86U and others. My model was in that list. The firmware version was past end of life, meaning that CVE was sitting there unpatched with no fix coming.

The decision

Putting a device with a known, unpatched, remote code execution vulnerability in a network security role is not a network security decision. I replaced it with a TP-Link TL-SG108E managed switch configured in a Router-on-a-Stick topology, with OPNsense on Proxmox handling all inter-VLAN routing. The managed switch handles 802.1Q VLAN tagging on the trunk port; OPNsense owns the routing logic and firewall rules between VLANs. No httpd daemon, no unpatched firmware sitting in the traffic path.

Outcome

CVE-2017-12754 mitigated TP-Link TL-SG108E deployed 802.1Q VLANs configured Router-on-a-Stick via OPNsense attack surface eliminated

This was a small decision in a home lab but the instinct behind it is the same one that matters in a production environment: verify before you deploy, check patch status, look for known CVEs, and don't trade convenience for exposure.

How I Found Out Wazuh's Built-in pfSense Ruleset Was Intercepting My OPNsense Firewall Logs

Deployed custom OPNsense filterlog decoders in Wazuh only to find the built-in pfSense ruleset was catching the events first. Both firewalls use the same log format, so Wazuh's pfSense decoder matched OPNsense logs too. The fix was inheritance, not a rewrite.

The goal

OPNsense generates filterlog events — structured firewall log entries that include interface, action (pass/block), source IP, destination IP, protocol, and port. Out of the box, Wazuh doesn't fully parse these. I wanted proper field extraction so I could write meaningful alert rules against them — things like "alert when traffic from VLAN 10 hits VLAN 20" or "flag outbound connections on unusual ports."

The plan was straightforward: write a custom Wazuh decoder targeting OPNsense filterlog format and extract the fields I needed.

What went wrong

I wrote and deployed the custom decoder, restarted Wazuh, sent test traffic through OPNsense, and watched the logs. The events were arriving but my decoder was never firing. After digging, I found the cause: Wazuh rule 87700, part of Wazuh's built-in pfSense ruleset, was matching the events before my custom decoder had a chance to run.

Here's why: pfSense and OPNsense both use the same filterlog format. They share the same BSD firewall logging standard, so Wazuh's built-in pfSense decoder correctly matched my OPNsense logs too — it had no way to tell them apart because the log structure is identical. This isn't a bug, it's just a consequence of both firewalls sharing the same log format ancestry.

Wazuh's decoder matching is hierarchical — once a parent decoder claims an event, only child decoders under that parent get to run. My custom decoder was defined as a standalone rule, not a child of the pfSense decoder, so it was being bypassed entirely every time.

Built-in rule
87700 (pfSense)
Log type
filterlog
Root cause
Decoder conflict
Fix
Parent inheritance

The fix

Instead of fighting the pfSense decoder, I worked with it. I updated my custom OPNsense rules to explicitly inherit from the pfSense parent decoder. Once my decoder was a child of rule 87700 rather than a standalone peer, Wazuh ran both in sequence — the parent matched the filterlog event (as it always had), and my child decoder then extracted the additional OPNsense-specific fields I needed on top of it.

The key lesson: when you're running OPNsense and Wazuh, you're not fighting the pfSense decoder — you're using it. Both firewalls produce the same filterlog format, so the built-in pfSense rules are your starting point, not your competition. Chain from them instead of trying to replace them.

Outcome

filterlog fields extracted custom decoder chained to pfSense parent rule 87700 conflict resolved OPNsense alerts firing correctly

Diagnosing a DHCP Failure After Moving My Firewall to a Closet

Relocated the Beelink mini PC and lost DHCP across the entire network. Root cause was a NIC assignment mismatch in OPNsense. Diagnosis took direct hardware testing and ended in a full OPNsense reinstall after a FreeBSD PAM error blocked every password reset path.

What happened

After physically relocating the Beelink mini PC to a closet for cleaner cable management, every device on the network lost DHCP. Nothing would get an address. The internet was still reachable via a direct connection, but nothing downstream of OPNsense was working.

Isolating the problem

My first thought was a physical cable issue. I reseated everything and verified switch ports, but the problem persisted. The next step was to remove variables systematically.

I connected a laptop directly to the Beelink, bypassing the managed switch and the downstream router entirely. If DHCP worked at that point, the problem was downstream. If not, the problem was OPNsense or the NIC assignment itself.

DHCP still failed on the direct connection. That ruled out everything downstream. The problem was inside OPNsense.

Root cause: NIC assignment mismatch

When the Beelink was relocated and powered back up, the two NICs had swapped their assigned roles in OPNsense. What OPNsense had mapped as the WAN interface was now physically connected to the LAN port, and vice versa. OPNsense was trying to hand out DHCP leases on what it thought was the LAN interface, but that interface was facing the wrong direction.

This is a known gotcha with mini PCs that have two identical NICs — there's no guarantee the OS enumerates them in the same order after a power cycle or physical move.

Why a simple fix didn't work

The straightforward fix would have been to log into OPNsense and reassign the NIC roles through the interface assignments page. But a FreeBSD PAM error was blocking every password reset attempt. The OPNsense shell is FreeBSD under the hood, and the PAM (Pluggable Authentication Module) error prevented the standard recovery paths from completing. Boot-time password reset options were also blocked in the state the VM was in.

At a certain point, time spent chasing a recovery path on a broken system exceeds the time it would take to redeploy cleanly. I wiped the OPNsense VM and reinstalled from a fresh ISO mounted in Proxmox.

The reinstall

Mounting the OPNsense ISO through Proxmox's virtual CD drive and booting from it was clean. During initial setup I carefully verified which physical NIC was WAN and which was LAN before confirming the interface assignments — exactly the step that caused the problem the first time. DHCP came back immediately on the first test. Reconfiguring VLAN setup, firewall rules, and syslog forwarding back to Wazuh took additional time, but everything was documented from the original build.

Outcome

NIC mismatch identified OPNsense reinstalled via Proxmox ISO DHCP restored VLAN + firewall rules reconfigured syslog forwarding re-established

The bigger lesson: document your interface assignments at build time. A label on the physical cable or a note with which MAC address corresponds to which role takes 30 seconds and would have made this a 2-minute fix instead of a full reinstall.
